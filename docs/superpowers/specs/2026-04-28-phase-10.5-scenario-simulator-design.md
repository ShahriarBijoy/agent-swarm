**Status:** drafted — pending user approval

**Decimal-insert rationale:** decided post-phase-10 merge (PR #13). Inserts a customer-driven demo loop on top of the operator dashboards before phase 11 (auth) freezes the public surface. Decimal numbering keeps phases 11/12 untouched.
**Constraints owner already set:**
- **No new agents.** `lib/agent/agents/index.ts:25` enforces the 11-agent headcount. Reshuffle = extend prompts + add domain MCP tools, never add registry entries.
- **Reuse vendored components.** `components/ui/deployment-card.tsx` is the vehicle card; `components/ui/map.tsx` (mapcn / maplibre-gl) is the map. No new map / card libraries.

## Purpose

Phase 10's dashboards prove "the swarm exists and you can watch it." Phase 10.5 closes the loop: **a customer can drive the swarm**.

A visitor types "I want to rent a vehicle for my weekend trip" into `/chat`. The dispatcher routes the request through the existing 11-agent swarm, which checks inventory, costs the trip, asks the operator (HITL) to confirm, books the vehicle, drafts an invoice, and (on a second HITL) charges it. The same dashboards from phase 10 keep showing what's happening live; three new surfaces — `/map`, `/billing`, and the live-trips card on the home — give the operator a domain-shaped view rather than a swarm-shaped view.

This is the phase that turns Auto-ride from "look at this swarm" into "watch this swarm rent a car."

Five things ship together because they share data and would deeply duplicate without bundling:

1. **Domain schema** — `vehicles`, `trips`, `customers`, `invoices`. Minimal columns; HNSW / vector / tsvector intentionally not added (no semantic search in this phase).
2. **Domain MCP tools** added to the existing in-process MCP server: `query_vehicles`, `compute_route`, `quote_rental`, `check_vehicle_health`, `get_trip_status`, `query_customer_history`, `flag_trip_incident`, `audit_approval`. Each tool is wired to one (sometimes two) of the existing agents via the `agents[].tools` allowlist; no agent gains write access to a table the spec doesn't say it owns.
3. **Agent prompt extensions** — every worker that needs domain knowledge gets a small appended block in its system prompt (rental scenarios, table shapes, HITL expectations). Dispatcher gets the routing matrix as an additional fragment.
4. **Three UI surfaces** — `/chat` (customer ingest), `/map` (live fleet), `/billing` (invoices + accounts). One new bento card on the existing home: "Trips on the road."
5. **Two HITL gate types** — `rental-confirm` and `payment-charge`. Both use the existing `approval_gates` table and the existing `<ApprovalRequest>` component; only the gate-payload schema is new.

Phase 11 (auth) gates `/chat` behind login and reads the customer from the session — that move is intentional and minimal because phase 10.5 already keeps `customers` separate from a future `users` table.

## Non-goals

- **No voice / Whisper / speech-to-text.** Text chat only. Voice is a phase 10.6 candidate if v0 lands clean.
- **No real maps tile API key.** Mapcn ships with Carto basemaps via maplibre-gl style URLs (no API key). We do not add Mapbox / Google.
- **No real route engine.** `compute_route` returns a deterministic mock (haversine distance + a 1.25× road factor + `distance_km / 60 km/h` ETA). A real OSRM / Google Directions adapter is out of scope.
- **No payment gateway.** `payment-charge` HITL marks `invoices.status = 'paid'` and writes a `payments` row only if we keep that table — see §5; no Stripe / no card capture.
- **No real-time vehicle telemetry.** "Vehicle on the road" position on `/map` is interpolated client-side between `pickup` and `dropoff` points by elapsed-time-vs-ETA fraction. Good enough for demo; honest about its mock nature in a tooltip.
- **No driver app / no driver-side UI.** `driver-coach` agent stays in the registry but receives no new tools this phase; the rental flow assumes self-drive rentals.
- **No multi-currency / tax engine.** USD only. `quote_rental` returns a flat 8.5% "service fee" line that stands in for tax — clearly labeled as a mock in the prompt.
- **No customer auth.** A `/chat` visitor identifies themselves by name + email in their first message; the agent calls `query_customer_history` to find or create the row. Phase 11 replaces this with a session lookup.
- **No new agents** — restated because it is the load-bearing constraint.
- **No reshuffling of `agentRegistry` order.** That ordering biases dispatcher routing (see header comment in `lib/agent/agents/index.ts`); changing it is out of scope.

## Cost check

Phase 10.5 **does** add Claude SDK calls during normal operation, unlike phase 10. Cost-relevant facts:

- **Per scenario** (rent-a-vehicle end-to-end, dispatcher + 3–4 workers + 2 HITL waits):
  - dispatcher (Opus 4.7): ~3 turns, ~2k input + ~1k output → ~$0.15
  - fleet-analyst (Haiku): 1 turn → ~$0.005
  - route-optimizer (Haiku): 1 turn → ~$0.005
  - billing (Haiku): 1 turn → ~$0.01
  - support (Haiku): occasional follow-up → ≤$0.01
  - **Total per rental scenario: ~$0.18**, well under the existing $1.00 per-task cap from phase 05 and the soft per-agent budgets in `lib/agent/agents/index.ts:50–60`.
- **Per status-query scenario:** dispatcher (~$0.05) + support (~$0.005) → **~$0.06**.
- **Embeddings:** zero new embedding calls. Memories continue to write per phase 04; the new domain tables are not embedded in this phase.
- **Neon:** four new tables, ~210 rows seeded total (**19 vehicles** — 3 trucks, 5 sedans, 4 vans, 7 SUVs — plus 25 customers, ~95 historical trips, ~95 invoices). Negligible. New indexes: `trips(status)`, `trips(vehicle_id)`, `invoices(status)`, `invoices(customer_id)` — all btree, all <50 KB at this scale.
- **Inngest:** unchanged event shape. New gate types reuse the existing `gate.${gateId}` event family from phase 07.

## Schema additions

```ts
// lib/db/schema.ts — appended after phase-09 tables

export const vehicleSegmentEnum = pgEnum('vehicle_segment', [
  'sedan', 'suv', 'van', 'truck',
]);                                                       // 4 segments only — see §"Fleet seed data"
export const vehicleStatusEnum = pgEnum('vehicle_status', [
  'available', 'in-use', 'maintenance',
]);
export const tripStatusEnum = pgEnum('trip_status', [
  'requested', 'confirmed', 'in-route', 'completed', 'cancelled',
]);
export const invoiceStatusEnum = pgEnum('invoice_status', [
  'draft', 'pending', 'paid', 'cancelled',
]);

export const vehicles = pgTable('vehicles', {
  id: uuid('id').defaultRandom().primaryKey(),
  plate: text('plate').notNull().unique(),
  make: text('make').notNull(),
  model: text('model').notNull(),
  year: integer('year').notNull(),
  segment: vehicleSegmentEnum('segment').notNull(),
  seats: integer('seats').notNull(),
  rangeKm: integer('range_km').notNull(),                 // tank or battery range
  odometerKm: integer('odometer_km').notNull().default(0),
  status: vehicleStatusEnum('status').notNull().default('available'),
  homeLat: doublePrecision('home_lat').notNull(),         // depot location
  homeLng: doublePrecision('home_lng').notNull(),
  imageSlug: text('image_slug').notNull(),                // public/vehicles/<slug>.png
  dailyRateUsd: numeric('daily_rate_usd', { precision: 10, scale: 2 }).notNull(),
  perKmRateUsd: numeric('per_km_rate_usd', { precision: 10, scale: 4 }).notNull(),
  lastServicedAt: timestamp('last_serviced_at', { withTimezone: true }),
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
}, (t) => [
  index('vehicles_status_idx').on(t.status),
  index('vehicles_segment_idx').on(t.segment),
]);

export const customers = pgTable('customers', {
  id: uuid('id').defaultRandom().primaryKey(),
  name: text('name').notNull(),
  email: text('email').notNull().unique(),
  phone: text('phone'),
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
});

export const trips = pgTable('trips', {
  id: uuid('id').defaultRandom().primaryKey(),
  customerId: uuid('customer_id').notNull().references(() => customers.id),
  vehicleId: uuid('vehicle_id').notNull().references(() => vehicles.id),
  status: tripStatusEnum('status').notNull().default('requested'),
  pickupLat: doublePrecision('pickup_lat').notNull(),
  pickupLng: doublePrecision('pickup_lng').notNull(),
  dropoffLat: doublePrecision('dropoff_lat').notNull(),
  dropoffLng: doublePrecision('dropoff_lng').notNull(),
  scheduledStartAt: timestamp('scheduled_start_at', { withTimezone: true }).notNull(),
  scheduledEndAt: timestamp('scheduled_end_at', { withTimezone: true }).notNull(),
  actualStartAt: timestamp('actual_start_at', { withTimezone: true }),
  actualEndAt: timestamp('actual_end_at', { withTimezone: true }),
  distanceKm: numeric('distance_km', { precision: 10, scale: 2 }).notNull(),
  totalCostUsd: numeric('total_cost_usd', { precision: 10, scale: 2 }).notNull(),
  polyline: jsonb('polyline').$type<Array<[number, number]>>().notNull(),  // [lat, lng] pairs for /map route render
  taskId: uuid('task_id').references(() => tasks.id),    // links the orchestration that created the trip
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
}, (t) => [
  index('trips_status_idx').on(t.status),
  index('trips_vehicle_id_idx').on(t.vehicleId),
  index('trips_customer_id_idx').on(t.customerId),
]);

export const invoices = pgTable('invoices', {
  id: uuid('id').defaultRandom().primaryKey(),
  tripId: uuid('trip_id').notNull().references(() => trips.id),
  customerId: uuid('customer_id').notNull().references(() => customers.id),
  amountUsd: numeric('amount_usd', { precision: 10, scale: 2 }).notNull(),
  taxUsd: numeric('tax_usd', { precision: 10, scale: 2 }).notNull(),

  status: invoiceStatusEnum('status').notNull().default('draft'),
  dueAt: timestamp('due_at', { withTimezone: true }).notNull(),
  paidAt: timestamp('paid_at', { withTimezone: true }),
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
}, (t) => [
  index('invoices_status_idx').on(t.status),
  index('invoices_customer_id_idx').on(t.customerId),
]);
```

## Domain MCP tools

All eight tools live in `lib/agent/mcp/domain-tools.ts` and are exposed via a second in-process MCP server (`createSdkMcpServer({ name: 'auto-ride-domain', tools: [...] })`). The orchestrator gets both servers (`memory` + `auto-ride-domain`); each agent's `tools` allowlist names only what the agent should be able to call.

| Tool | Args (Zod) | Returns | Side effect |
|---|---|---|---|
| `query_vehicles` | `{ status?, segment?, seats_min?, range_min_km? }` | `Array<{id, plate, make, model, segment, seats, range_km, daily_rate_usd, per_km_rate_usd, image_slug, status, home_lat, home_lng}>` | none |
| `compute_route` | `{ pickup: {lat,lng}, dropoff: {lat,lng}, vehicle_id?: uuid }` | `{ distance_km, eta_minutes, polyline: Array<[lat,lng]>}` | none — haversine × 1.25; polyline is a 32-point linear interpolation between pickup and dropoff (good enough for `/map` render; real OSRM is phase 12) |
| `quote_rental` | `{ vehicle_id: uuid, distance_km: number, days: number }` | `{ base_usd, per_km_usd, insurance_usd, service_fee_usd, total_usd, breakdown: string[] }` | none |
| `check_vehicle_health` | `{ vehicle_id: uuid }` | `{ ok: boolean, last_serviced_at, odometer_km, flags: string[] }` | none |
| `get_trip_status` | `{ trip_id: uuid }` \| `{ customer_email: string }` | `{ trip, vehicle, customer, current_position?: {lat,lng} }` | none |
| `query_customer_history` | `{ email?: string, customer_id?: uuid }` | `{ customer, trips: Trip[], total_spend_usd }` (creates row if `email` doesn't match) | **inserts into `customers`** if no match — gated below |
| `flag_trip_incident` | `{ trip_id: uuid, severity: 'low'\|'med'\|'high', note: string }` | `{ ok: true, incident_id }` | **inserts incident row + bumps `trips.status` if severity='high'** — gated below |
| `audit_approval` | `{ gate_id: uuid }` | `{ gate, decided_by, decided_at, payload }` | none |

**Allowlist matrix (the load-bearing reshuffle):**

| Tool | Granted to |
|---|---|
| `query_vehicles` | fleet-analyst, analytics-reporter, support |
| `compute_route` | route-optimizer |
| `quote_rental` | billing |
| `check_vehicle_health` | fleet-analyst, maintenance-planner |
| `get_trip_status` | support, analytics-reporter |
| `query_customer_history` | support (writes via HITL — see below), analytics-reporter (read-only path; the tool is the same but `support` is the only agent with the prompt that ever creates) |
| `flag_trip_incident` | incident-responder |
| `audit_approval` | compliance-auditor |

`reflector` and `driver-coach` get no new tools.

**Tools that write are HITL-gated**, not allowlist-gated: `query_customer_history`'s create path is wrapped in a `canUseTool` check that opens a `customer-create` gate when `email` is unknown; `flag_trip_incident` opens an `incident-flag` gate at severity='high'. Phase 07's gate dispatcher already handles arbitrary gate types — only the new payload schemas are added.

**Two new HITL gate types** (full schemas in `lib/agent/hitl/types.ts`):

| Gate | Opened by | Payload | Visible to operator |
|---|---|---|---|
| `rental-confirm` | dispatcher when proposing a vehicle | `{ vehicle, customer, scheduled_start_at, scheduled_end_at, distance_km, total_usd, breakdown }` | "Approve rental: 2024 Honda CR-V for Ana Khan, Apr 30 → May 2, 612 km, $284.50?" |
| `payment-charge` | billing when ready to charge | `{ invoice_id, customer, amount_usd, vehicle_plate }` | "Charge $284.50 to ana@…?" |

Both reuse `<ApprovalRequest>` from `components/timeline/`. Only the payload-renderer dispatch in `<ApprovalRequest>` gets two new branches — same pattern phase 07 used for `bash-exec` and `write-file`.

## Agent prompt extensions

Each affected agent gets one new section appended to its existing system prompt, gated by a constant so the addition is greppable and removable:

```ts
// lib/agent/agents/fleet-analyst.ts (illustrative; same pattern for all 8)
const RENTAL_SCENARIO_PROMPT = `

## Rental scenario context (phase 10.5)

You operate against a fleet of small road vehicles. Customers ask to rent a vehicle for a trip.

When dispatched on a rental request:
- Use \`query_vehicles\` to find candidates matching the customer's seat count, range needs, and segment.
- Use \`check_vehicle_health\` on each finalist; do not propose a vehicle whose \`flags\` is non-empty.
- Return a short JSON-shaped recommendation (max 3 vehicles) so the dispatcher can hand it to billing.

Do not quote prices — that is billing's job. Do not compute routes — that is route-optimizer's job.
`;
```

The dispatcher's `dispatcher-prompt.ts` gets the routing matrix:

```
Rental request → fleet-analyst (find), route-optimizer (route), billing (quote), HITL rental-confirm,
                 → on approve: billing creates invoice, HITL payment-charge, → on approve: trip status='confirmed'.
Trip-status query → support (lookup), optionally analytics-reporter (history).
Incident report → incident-responder (flag, gated at severity='high').
```

These prompt fragments are unit-tested by `tests/agents/definitions.test.ts` (existing) — we extend the existing assertion that "the prompt mentions the agent's primary tool" to cover the new tools.

## UI surfaces

### `/chat` (customer ingest)

Single-textarea page, two seed prompts as one-click suggestions:

> "I want to rent a vehicle for my weekend trip — 4 people, ~600 km round trip, leaving Friday afternoon."
> "What's the status of my trip? My email is ana@example.com."

**Customer identity:** until phase 11 wires sessions, we accept `?customer=<email>` as a query-string prefill on `/chat`. The chat form pre-fills a small "Replying as: ana@example.com" pill and includes that email in the POST body so the orchestrator can route to `query_customer_history` without re-asking. If absent, the agent prompts for an email mid-conversation (handled by `support`'s prompt extension).

Submit → server action → `POST /api/tasks` with body `{ kind: 'scenario', prompt, customer_email? }`. The existing `/api/tasks` route (phase 06) is extended to recognize `kind: 'scenario'` and seed the orchestrator with the scenario prompt prefix. Redirects to `/tasks/[id]` (phase 10's canvas) so the customer can watch the swarm work — same view the operator sees.

### `/map` (live fleet)

Full-page mapcn map. Markers:
- green dot — `vehicles.status = 'available'` (positioned at `homeLat`/`homeLng`)
- amber dot — `vehicles.status = 'in-use'` (interpolated position along its current trip's route)
- red dot — `vehicles.status = 'maintenance'` (positioned at depot)

**Routes:** for every `in-use` vehicle we render its trip route as a polyline using mapcn's `<MapRoute>` (https://www.mapcn.dev/docs/routes). The route is the trip's `polyline` field (returned from `compute_route` and stored on the trip row at confirm-time). The amber marker sits at `polylineProgress = elapsed / eta` along the line. Routes auto-fade when the vehicle returns to `available`.

Click a marker → side panel slides in with the **vehicle card** (`components/vehicles/vehicle-card.tsx`) — the deployment-card visual filled with vehicle data. Polls `/api/vehicles` every 5 s.

> Add `polyline jsonb` to the `trips` schema (array of `[lat, lng]` pairs) — small addition to the schema in §"Schema additions" below; updated there too.

### `/billing` (invoices + accounts)

Three sections:
1. **Pending charges** — invoices with `status IN ('draft','pending')`, sortable by `due_at`. Each row has an "open task" link to the orchestration that produced it.
2. **Paid ledger** — invoices with `status = 'paid'`, last 90 days.
3. **Top customers** — `query_customer_history`-style aggregate, top-10 by spend.

No write actions on this page in v0; payment-charge happens via the HITL gate in the canvas.

### Live-trips card on the home

New widget in `components/dashboard/widgets/trips-on-road.tsx`, registered into the bento via `widget-registry.ts`. Shows up to 5 in-progress trips with: customer first name, vehicle plate, ETA remaining, mini progress bar (elapsed vs scheduled-end). Polls `/api/trips?status=in-route` every 3 s (matches phase 10's polling cadence).

## Two seed scenarios (end-to-end)

**A — Rent a vehicle**

1. Customer submits prompt at `/chat` with email + trip params.
2. Orchestrator (Sonnet 4.6) reads scenario prefix, dispatches to:
   - `fleet-analyst` → `query_vehicles` → 3 candidates → `check_vehicle_health` → 2 finalists.
   - `route-optimizer` → `compute_route` for each finalist → distance + ETA.
   - `billing` → `quote_rental` for the cheapest finalist → total + breakdown.
3. Dispatcher opens **`rental-confirm` HITL gate** with the proposed vehicle + total. Inngest `step.waitForEvent` per phase 07.
4. On approve → `billing` writes `trips` + `invoices(status='draft')` rows (gated only by canUseTool's allow on the gate-level decision; no extra gate). Trip `task_id` set to current task.
5. `billing` opens **`payment-charge` HITL gate**.
6. On approve → `invoices.status='paid'`, `paid_at=now()`. Reflector writes a memory of the run.
7. Customer's `/tasks/[id]` view shows the canvas with both gates, the dashboards' kanban moves the task through `in-progress → awaiting-approval → done`, the new `trips-on-road` card lights up.

**B — Trip status**

1. Customer submits "what's my trip status?" + email.
2. Dispatcher → `support` → `get_trip_status({customer_email})` → returns trip + vehicle + position.
3. Optionally → `analytics-reporter` → `query_customer_history` for spend context.
4. Reply rendered in the canvas (no HITL gate; read-only).

## Vehicle card — DeploymentCard mapping (per type)

The deployment-card visual is fixed; only the data shape varies. For each segment type, here are the **exact strings** the card renders, parameterized by the row above:

| Card slot | Source expression | Truck example | Sedan example | Van example | SUV example |
|---|---|---|---|---|---|
| `id` (large title) | `vehicle.plate` | `AR-T-2301` | `AR-S-2401` | `AR-V-2401` | `AR-X-2401` |
| `environment` (UPPER tag) | `vehicle.segment.toUpperCase()` | `TRUCK` | `SEDAN` | `VAN` | `SUV` |
| `status` (badge) | `available→Ready, in-use→Building, maintenance→Error` | Ready | Building | Building | Building |
| `createdBy.name` (small UPPER badge) | `${make} ${model}` | `Ford F-150` | `Honda Accord` | `Toyota Sienna` | `Honda CR-V` |
| `createdTime` | `${year} · ${odometerKm.toLocaleString()} km` | `2023 · 18,420 km` | `2024 · 6,910 km` | `2024 · 9,840 km` | `2024 · 12,030 km` |
| `duration` (mono) | `${rangeKm} km · ${seats}p` | `800 km · 5p` | `650 km · 5p` | `550 km · 8p` | `720 km · 5p` |
| `lastActive` | days since `lastServicedAt`, fmt `serviced ${n}d ago` | `serviced 12d ago` | `serviced 5d ago` | `serviced 21d ago` | `serviced 8d ago` |
| `domains[0]` | `in-use → trip-${tripId.slice(0,8)}.in-route` else `${depot}.idle` else `service.bay-${1-3}` | `fleet-east.idle` | `trip-d4f1e2a8.in-route` | `trip-9c3b1e07.in-route` | `trip-71fb24ce.in-route` |
| `branch` (git-branch chip) | `vehicle.depot` | `fleet-east` | `fleet-east` | `fleet-east` | `fleet-east` |
| `commitMessage` | in-use → `Group of ${seats} → ${city}, ${distanceKm}km` else `Idle in depot · $${dailyRateUsd}/day` | `Idle in depot · $185/day` | `Group of 5 → Cape Cod, 612km` | `Group of 8 → Cape Cod, 612km` | `Group of 4 → Tahoe, 384km` |
| `commitHash` (mono) | in-use → `tripId.slice(0,7)` else `vehicleId.slice(0,7)` | `b71-2a4` | `d4f1e2a` | `9c3b1e0` | `71fb24c` |
| `imagePreviewUrl` (NEW prop) | `/vehicles/${imageSlug}.png` (placeholder.svg until PNG dropped) | `/vehicles/ford-f-150.png` | `/vehicles/honda-accord.png` | `/vehicles/toyota-sienna.png` | `/vehicles/honda-cr-v.png` |
| `steps[0]` Pickup | progress=1 status=success when `actualStartAt` set; else pending | success (idle: pending) | success | success | success |
| `steps[1]` In-route | `progress = clamp((now - actualStartAt) / etaMs, 0, 1)`; status=loading when 0<p<1 | pending | loading 0.42 → `4m 12s` | loading 0.18 → `1m 51s` | loading 0.71 → `7m 03s` |
| `steps[2]` Drop-off | success when `actualEndAt` set; else pending | pending | pending | pending | pending |
| `steps[3]` Return | success when `vehicle.status='available'` after a trip; else pending | pending | pending | pending | pending |

For `available` vehicles all four steps are `pending` and the card reads as a passive spec sheet — which is exactly what an idle vehicle should look like. For `maintenance` vehicles `steps[0]` flips to `error` with a one-line note ("scheduled service") and the rest stay pending.

The adapter is pure, total, and unit-tested by `tests/adapters/vehicle-to-deployment.test.ts`.
