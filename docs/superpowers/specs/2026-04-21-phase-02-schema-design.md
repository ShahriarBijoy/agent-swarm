# Phase 02 — Schema (design)

**Date:** 2026-04-21
**Status:** approved (brainstorming)
**Plan references:** `auto-ride-initial-plan.md` §5, §6
**Roadmap entry:** `docs/roadmap/ROADMAP.md` — phase 02

## Purpose

Define the persistent data model for Auto-ride: five memory tables, a task/run/event trio, one approval-gate table, six enums, the critical indexes that make hybrid retrieval cheap, and seven seeded `memory_segment_config` rows. Phase 02 ships **DDL + types only** — no embedding generation, no retrieval SQL, no agent code. Later phases import these tables as-is.

## Non-goals

Explicitly out of scope — do not add them even if convenient:

- Embedding generation or Gemini SDK (phase 03).
- The hybrid-search SQL expression / `recall` MCP tool (phase 03).
- Write / reinforce / forget logic and decay formulas (phase 04).
- Any `query()` / orchestrator / subagent code (phase 05).
- SSE endpoint or task-runner wiring (phase 06).
- `canUseTool` / Inngest `waitForEvent` (phase 07).
- Nightly cleanup job, Consolidator–Adversary–Judge prompts (phase 09).

Phase 02 defines the *shape* these features plug into; it does not implement any of them.

## Cost check

Zero incremental cost. Phase 02 uses only the Neon project already wired in phase 01 (free tier) and the Drizzle/pnpm toolchain already installed. **No Anthropic API calls, no Gemini embedding calls, no new paid services.** The Max-subscription OAuth path is untouched until phase 05.

## Dependencies

**Already installed (phase 01):** `drizzle-orm@^0.45.2`, `drizzle-kit@^0.31.10`, `postgres@^3.4.9`, `@neondatabase/serverless@^1.1.0`, `zod@^4`. All sufficient for phase 02 — **no new dependencies added**.

**Confirmed Drizzle APIs** (verified against current docs before writing this spec):

| Need | API | Import |
|---|---|---|
| 1536-dim vector column | `vector('embedding', { dimensions: 1536 })` | `drizzle-orm/pg-core` |
| Generated stored tsvector | `customType<{ data: string }>({ dataType() { return 'tsvector'; } })` + `.generatedAlwaysAs(sql\`...\`)` | `drizzle-orm/pg-core` + `drizzle-orm` |
| HNSW + cosine + WITH-params + partial | `index(...).using('hnsw', col.op('vector_cosine_ops')).with({ m, ef_construction }).where(sql\`...\`)` | `drizzle-orm/pg-core` |

Postgres always stores generated columns (no virtual/stored toggle), so Drizzle omits `mode: 'stored'` — the `STORED` keyword is emitted automatically.

## Directory layout

Phase 01 chose a flat layout (no `src/`); phase 02 follows that. Schema is split by domain into one file per concern, re-exported from a barrel. This keeps migrations diff-friendly and makes it obvious where to add the next table.

```
Agent-swarm/
├── db/
│   ├── client.ts              # unchanged from phase 01
│   └── schema/
│       ├── index.ts           # barrel: re-exports everything
│       ├── enums.ts           # 6 pg enums
│       ├── types.ts           # customType helpers (tsvector)
│       ├── memories.ts        # memories + memory_segment_config + memory_links
│       ├── cleanup.ts         # memory_cleanup_runs + memory_cleanup_proposals
│       ├── tasks.ts           # tasks + task_runs + task_events
│       └── approvals.ts       # approval_gates
├── drizzle/
│   ├── 0000_enable_vector.sql                # phase 01
│   ├── 0001_core_schema.sql                  # NEW — auto-generated by drizzle-kit
│   ├── 0002_seed_segment_config.sql          # NEW — custom, idempotent INSERTs
│   └── meta/                                  # drizzle-kit journal (updated)
└── tests/
    └── schema.test.ts         # NEW — catalog introspection tests
```

Splitting by domain (memories vs tasks vs approvals vs cleanup) is deliberate — later phases edit one domain at a time, and the file boundaries keep PR diffs reviewable. `enums.ts` and `types.ts` are shared imports to avoid circular references.

## Enum inventory

Six pg-native enums. All values lowercase snake_case. Text columns preferred where values might evolve (see `task_events.type`).

| Enum | Values | Used by |
|---|---|---|
| `segment` | `identity`, `correction`, `preference`, `relationship`, `knowledge`, `behavioral`, `context` | `memories.segment`, `memory_segment_config.segment` |
| `bucket` | `short`, `long`, `permanent` | `memories.bucket` |
| `task_status` | `queued`, `in_progress`, `awaiting_approval`, `done`, `failed`, `cancelled` | `tasks.status`, `task_runs.status` |
| `approval_status` | `pending`, `approved`, `modified`, `denied`, `timed_out` | `approval_gates.status` |
| `cleanup_action` | `promote`, `prune`, `merge`, `keep` | `memory_cleanup_proposals.action`, `memory_cleanup_proposals.final_action` |
| `link_type` | `merged`, `superseded` | `memory_links.link_type` |

**Why `task_events.type` is `text`, not an enum:** SDK message shapes evolve with each alpha release (`auto-ride-initial-plan.md` §8 lists SDK churn as a top-five risk). A `text` column with a CHECK constraint listing the known values at phase 02 is cheaper to extend than `ALTER TYPE ADD VALUE`. Known values for phase 06: `assistant_turn`, `tool_call`, `tool_result`, `approval_request`, `compact_boundary`, `run_result`, `user_message`.

## Table designs

Each table lists columns and noteworthy constraints. Drizzle-specific syntax lives in the implementation plan; the spec captures shape and intent.

### `memories` — the heart of the system

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK, `defaultRandom()` | |
| `segment` | `segment` enum NOT NULL | |
| `bucket` | `bucket` enum NOT NULL DEFAULT `'short'` | promotion logic in phase 04 |
| `content` | `text` NOT NULL | ≤ ~8 KB realistic; no hard limit |
| `content_tsv` | `tsvector` GENERATED ALWAYS AS `to_tsvector('english', content)` STORED | GIN-indexed |
| `embedding` | `vector(1536)` | nullable until phase 03 populates |
| `importance` | `numeric(3,2)` NOT NULL DEFAULT segment default | 0.00–1.00 |
| `importance_streak` | `integer` NOT NULL DEFAULT 0 | days-above-threshold, drives promotion (phase 04/09) |
| `access_count` | `integer` NOT NULL DEFAULT 0 | |
| `created_at` | `timestamptz` NOT NULL `defaultNow()` | |
| `last_accessed_at` | `timestamptz` NOT NULL `defaultNow()` | drives decay in phase 04 |
| `tombstoned_at` | `timestamptz` NULL | soft-delete, 14-day reversible window |
| `metadata` | `jsonb` NOT NULL DEFAULT `'{}'::jsonb` | agent-/segment-specific fields |

**Indexes:**

- `memories_pk` — primary key on `id`.
- `memories_embedding_hnsw_idx` — HNSW on `embedding` with `vector_cosine_ops`, `WITH (m = 16, ef_construction = 64)`, partial `WHERE tombstoned_at IS NULL`.
- `memories_content_tsv_gin_idx` — GIN on `content_tsv`, partial `WHERE tombstoned_at IS NULL`.
- `memories_decay_btree_idx` — compound btree on `(bucket, importance DESC, last_accessed_at DESC)`, partial `WHERE tombstoned_at IS NULL`. Feeds the nightly-candidate SQL in phase 09.
- `memories_segment_tombstone_idx` — btree on `(segment, tombstoned_at)`. Makes segment-filtered admin views fast (phase 10).

All secondary indexes are partial on `tombstoned_at IS NULL` because ~100% of hot-path reads exclude tombstoned rows. The 14-day undelete window pulls from the un-indexed minority.

**Why `numeric(3,2)` for importance:** precision matters for the reinforcement boost `I ← min(1.0, I + 0.05·(1 − I))` and for `importance_streak` threshold comparisons. `double precision` drifts in visible ways after ~40 reinforcement iterations. `numeric` arithmetic in Postgres is plenty fast at this scale.

### `memory_segment_config` — tunable segment defaults

| Column | Type | Notes |
|---|---|---|
| `segment` | `segment` enum PK | one row per segment |
| `default_importance` | `numeric(3,2)` NOT NULL | 0.90/0.80/0.70/0.65/0.60/0.55/0.40 |
| `decay_lambda_short` | `double precision` NOT NULL | `-ln(0.92) ≈ 0.0834` default |
| `decay_lambda_long_factor` | `double precision` NOT NULL DEFAULT `0.01` | phase 04 formula: `λ_long = factor · (1 − 0.8·I)` |
| `promotion_threshold_long` | `numeric(3,2)` NOT NULL DEFAULT `0.50` | |
| `promotion_threshold_permanent` | `numeric(3,2)` NOT NULL DEFAULT `0.80` | |
| `fast_track_permanent` | `boolean` NOT NULL DEFAULT `false` | `identity` is the only `true` in seeds |
| `updated_at` | `timestamptz` NOT NULL `defaultNow()` | |

**Seeded rows** (migration `0002_seed_segment_config.sql` with `ON CONFLICT (segment) DO NOTHING`):

```

correction   0.80
preference   0.70
relationship 0.65
knowledge    0.60
behavioral   0.55
```

Lambda defaults match `auto-ride-initial-plan.md` §5. Phase 04 reads this table to compute effective importance at query time (or via a generated column / view).

### `task_events` — append-only SSE feed

Every SDK message persists here. The phase 06 SSE endpoint tails this table.

| Column | Type | Notes |
|---|---|---|
| `id` | `bigserial` PK | bigserial gives cheap strict ordering for SSE |
| `run_id` | `uuid` NOT NULL → `task_runs.id` ON DELETE CASCADE | |
| `task_id` | `uuid` NOT NULL → `tasks.id` | denormalized for cheap task-level tails |
| `seq` | `integer` NOT NULL | monotonic per run, set by writer |
| `type` | `text` NOT NULL CHECK `in (…)` | see enum-vs-text note above |
| `payload` | `jsonb` NOT NULL | full SDK message |
| `created_at` | `timestamptz` NOT NULL `defaultNow()` | |

**Indexes:** btree on `(task_id, id)`, btree on `(run_id, seq)`, UNIQUE on `(run_id, seq)`.

`id` as `bigserial` instead of `uuid` is deliberate: SSE wants a strict total order, and `bigserial` is the cheapest way to get one without clock skew.

## Migration strategy

Two new migrations, in order. Run `pnpm db:generate` to produce `0001_core_schema.sql` from the Drizzle schema; run `pnpm exec drizzle-kit generate --custom --name seed_segment_config` to scaffold `0002_…_seed_segment_config.sql` and hand-edit it to contain idempotent INSERTs.

```
drizzle/
├── 0000_enable_vector.sql              # phase 01 — CREATE EXTENSION
├── 0001_core_schema.sql                # phase 02 — all enums, tables, indexes
└── 0002_seed_segment_config.sql        # phase 02 — 7 INSERT … ON CONFLICT DO NOTHING
```

Why split DDL from seeds: re-running `db:generate` in phase 03/04 should regenerate DDL deltas cleanly without re-touching seed INSERTs. Keeping seeds in their own migration means `drizzle-kit generate` never hallucinates diffs against seed data.

**After `db:generate` produces `0001_core_schema.sql`, review it by hand** — Drizzle's custom-type support for tsvector is stable but the generated SQL for `GENERATED ALWAYS AS … STORED` is worth eyeballing once. Same for the HNSW `WITH` clause. Commit the generated SQL unchanged if it looks correct; edit in place if not.

## Testing

One new test file, `tests/schema.test.ts`, exercised with `pnpm test`. It connects using `DATABASE_URL_UNPOOLED` (so it runs after `pnpm db:migrate`) and asserts:

1. All nine tables exist (catalog query on `information_schema.tables`).
2. All six enums exist with the correct values (`pg_type` + `pg_enum`).
3. The HNSW, GIN, and compound btree indexes exist on `memories` with the expected predicates (`pg_indexes.indexdef`).
4. The seven `memory_segment_config` rows exist with correct `default_importance` values.
5. `INSERT INTO memories (segment, content) VALUES ('knowledge', 'hello')` succeeds (DEFAULT values fill).
6. `INSERT INTO memories (segment, content, embedding) VALUES ('knowledge', 'x', '[1,2,3]'::vector)` fails with a dimension mismatch error.
7. Running `pnpm db:migrate` a second time is a no-op (idempotency — no duplicate seeds, no re-created indexes).

Tests run against the live Neon project. They are skipped automatically if `DATABASE_URL_UNPOOLED` is unset (CI path in phase 12 will provide a separate ephemeral DB).

## Acceptance criteria

All must pass before the phase 02 PR merges:

1. `pnpm db:generate` produces a clean migration with no unrelated diffs; committed as `0001_core_schema.sql`.
2. `pnpm db:migrate` applies `0001` and `0002` cleanly from a DB that only has `0000_enable_vector.sql` applied.
3. `pnpm db:studio` renders all nine tables with the expected columns and FK arrows.
4. `pnpm test` passes all seven schema assertions above.
5. `pnpm typecheck` passes (strict mode, `noUncheckedIndexedAccess`).
6. `pnpm lint` passes.
7. `pnpm build` passes (the `/health` route still works — phase 01 regression check).
8. Running `pnpm db:migrate` a second time reports "no migrations to run" / applies nothing new.
9. Manual: on Neon's dashboard, `SELECT COUNT(*) FROM memory_segment_config` returns `7`.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Drizzle-kit emits a wrong `GENERATED ALWAYS AS` SQL for tsvector | Medium | Acceptance criterion #1: review `0001_core_schema.sql` before committing; fall back to a `--custom` migration for the tsvector column only if needed |
| HNSW `WITH` clause not emitted correctly | Low | Inspect generated SQL against `CREATE INDEX … USING hnsw (…) WITH (m = 16, ef_construction = 64)` template; correct syntax is documented in pgvector README |
| Seed migration non-idempotent → duplicates on re-run | Medium | Use `INSERT … ON CONFLICT (segment) DO NOTHING` explicitly; covered by test #7 |
| `task_events.id` as `bigserial` and `uuid` task ids mixed in SSE reasoning | Low | Document in the `/api/tasks/[id]/stream` design (phase 06); events cursor is `id`, not `created_at` |
| `numeric(3,2)` importance cast-mismatch in JS | Low | Drizzle reads `numeric` as `string`; phase 04 helpers parse/format explicitly (documented there) |
| pgvector version on Neon missing HNSW (< 0.5.0) | Very low | Neon ships 0.7+ on the free tier (confirmed phase 01); test #3 catches regressions |
| `CREATE TYPE` during migration on a populated DB takes an exclusive lock | N/A in phase 02 | Phase 02 runs against an empty DB; future enum changes will need careful planning (noted for phase 10) |

## What unlocks next

Phase 02 passing unlocks **phase 03 (memory MCP — read)**. Phase 03 uses:

- `memories` with embedding + tsvector columns ready to query.
- The HNSW + GIN + btree indexes for the hybrid-search SQL.
- The seven `memory_segment_config` rows for segment-aware defaults.
- The types re-exported from `db/schema/index.ts` for Drizzle `select(...)` call-sites.

Phase 04 reuses the same `memories` row to add write/reinforce/forget flows. Phase 05's orchestrator-to-subagent event stream lands in `task_events`. Phase 07's approval flow lands in `approval_gates`. None of those phases touch the DDL — only the data.
